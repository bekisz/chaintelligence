Chaintelligence API — JSON:API Compound Documents

The analytic endpoints (/api/od/*, /api/ods/*, /api/routes/*, /api/coins/*, /api/coin-families, /api/pool/*) return JSON:API compound documents. Related resources are not nested inline; the primary resource(s) live in data (a single object for one result, an array for many), and every linked resource is deduplicated in the top-level included array. Relationships point at included resources by type:id.

The object graph

od ── routes (many) ── hops (many) ── pool ── coin0
 │        │                              │        coin1
 │        └─ chain                       └─ chain
 ├─ origin_coin      (coin)
 └─ destination_coin (coin)

coin ── contracts (many, coin_contract: chain/address/decimals)
       └─ families (many, coin_family ── members (many, coin))

chain ── id + name

Every id is a string. Route ids are the 16-char lowercase hex form (e.g. 837dc52fa8bde82c) used by /api/routes/{route_hash}; hop ids are {route_hash}:{seq}. O&D ids (od_hash) are also 16-char hex, pool ids are the numeric liquidity-pool id, and coin ids are the numeric coin id.

Control what you get with ?include=

The default is intentionally slim. Append a comma-separated list of dot-paths to embed more of the graph. Paths are validated against the schema — an unknown segment returns 400 with a detail explaining the valid relationships for that resource. 

# Just the pair row, no relatives
curl -u admin -H 'Authorization: Basic ...' \
  "http://localhost:8000/api/od/2ac53c78a580597e?include="

# Pair + its routes + each hop
curl "http://localhost:8000/api/od/2ac53c78a580597e?include=routes.hops"

# Full drill-down: routes → hops → pool → the pool's two coins
curl "http://localhost:8000/api/od/2ac53c78a580597e?include=routes.hops.pool,routes.hops.pool.coin0,routes.hops.pool.coin1"

Slim it down with ?fields[type]=

Sparse fieldsets limit the attributes returned for each type. Apply per resource type, comma-separated attribute names. 

# Only hop seq/symbols and pool fee/TVL — no coin metadata
curl "http://localhost:8000/api/routes/837dc52fa8bde82c?include=hops.pool&fields[hop]=seq,token_in_symbol,token_out_symbol&fields[pool]=fee_bps,tvl_usd"

Reading the response

  • data — the primary resource (object if exactly one, array if many or none).
  • included — every linked resource, deduplicated by type:id.
  • meta.n — how many primary resources matched; list endpoints add limit/offset.
  • links.self — the canonical URL of this request.
  • Errors use {"detail": ...} with status 400 (bad include/fields/identifier), 404 (not found) or 500.

O&D Sets — match pairs declaratively

GET /api/ods/set returns every origin/destination pair matching an O&D Set definition. Each side selector is resolved like the routing search bar: a coin symbol (WBTC), a coin family (BTC, USD — expands to all member coins), * (every coin), or a coin contract address (0x…). direction=both (default) also returns each pair reversed; direction=forward keeps only origin → dest. chains is a comma-separated chain list. 

# Every BTC-family <-> USD-family pair on Ethereum, both orientations
curl "http://localhost:8000/api/ods/set?origin=BTC&dest=USD&direction=both&chains=Ethereum&include=routes"

# All USDC pairs across Ethereum and Base, forward orientation only
curl "http://localhost:8000/api/ods/set?origin=*&dest=USDC&direction=forward&chains=Ethereum,Base"

# One side given by contract address
curl "http://localhost:8000/api/ods/set?origin=0x2260fac5e5542a773aa44fbcfedf7c193bc2c599&dest=USD"

O&D goal-state — data-coverage governance

GET /api/ods/goal-state is the read-only report side of the goal-state retention engine. It evaluates every requirement in config/ods-goal-state.yaml across the governed layers (swaps, route_daily_stats, route_daily_stats_bucket, liquidity_pool) against the warehouse and reports each as ok/partial/missing/stale plus the specific days missing. The requirement side-selectors share the same semantics as /api/ods/set; a more specific requirement (contract > symbol > family > *, specific chain > *) overrides less specific ones, so coverage follows the effective windows. Pruning itself runs in the ods_goal_state_retention Airflow DAG or the CLI (chain-feeder/include/scripts/ods_goal_state.py); add estimate=true to dry-run the delete counts. 

# Coverage + gaps for every requirement
curl "http://localhost:8000/api/ods/goal-state"

# Same report + how many rows a prune would delete per layer
curl "http://localhost:8000/api/ods/goal-state?estimate=true"

Daily stats & bucket distribution

Every route carries pre-aggregated daily stats (route_daily_stats: volume, fees, tx/swap counts per day) and a log-volume bucket distribution (route_daily_stats_bucket: one row per route+day+bucket). Both are read models backing /api/routes/analyze and /api/swap-distribution — no raw-swaps reads. 

# One route's daily stats + bucket distribution in a single request
curl "http://localhost:8000/api/routes/837dc52fa8bde82c/daily-stats"

# Same data reachable through the route resource via include
curl "http://localhost:8000/api/routes/837dc52fa8bde82c?include=daily_stats,daily_stats_bucket"

# ... or nested under the od drill-down
curl "http://localhost:8000/api/od/2ac53c78a580597e?include=routes.daily_stats"

# Just the day-level rollups, slimmed to two fields
curl "http://localhost:8000/api/routes/837dc52fa8bde82c/daily-stats?include=daily_stats&fields=route_daily_stat[day,volume_usd]"

route_daily_stat ids are {route_hash}:{day} (e.g. 837dc52fa8bde82c:2026-08-13); route_daily_stat_bucket ids are {route_hash}:{day}:{bucket_index}. Each daily stat links to its same-day buckets via daily_stats_bucket. Fields: day, tx_count, swap_count, volume_usd, fees_usd (stats); + bucket_index, sample_count, log_sum, log_sum2 (buckets).

A window_stats attribute on the route resource gives the window-aggregated sums and derived metrics over a date range — the same numbers /api/routes/analyze reports per route (count, swaps, volume, market_size, avg_volume, pct_volume, last_activity). Pass days or start_date/end_date; without them it covers the route's full available range: 

# Last 7 days of aggregated route activity
curl "http://localhost:8000/api/routes/837dc52fa8bde82c/daily-stats?days=7"

# Explicit window; window_stats.tx_count/swaps/volume/fees are the day-range sums
curl "http://localhost:8000/api/routes/837dc52fa8bde82c/daily-stats?start_date=2026-08-01&end_date=2026-08-15"

# Just the window aggregate, nothing else
curl "http://localhost:8000/api/routes/837dc52fa8bde82c/daily-stats?fields=route[window_stats]"

Pool daily stats

Pools have the same two read models — liquidity_pool_daily_stats (per pool+day: volume, TVL, tx count) and liquidity_pool_daily_stats_bucket (per pool+day+bucket). Use the pool identifier (numeric id, V3 contract address, or V4 pool_id) with the same path suffix: 

# One pool's daily stats + bucket distribution
curl "http://localhost:8000/api/pool/165681/daily-stats"

# By V3 contract address
curl "http://localhost:8000/api/pool/0x88e6a0c2ddd26feeb64f039a2c41296fcb3f5640/daily-stats"

# Volume per day only
curl "http://localhost:8000/api/pool/165681/daily-stats?include=daily_stats&fields=pool_daily_stat[day,volume_usd]"

# Fees per bucket (one resource per pool+day+bucket)
curl "http://localhost:8000/api/pool/165681/daily-stats?fields=pool_daily_stat_bucket[day,bucket_index,fees_usd]"

pool_daily_stat ids are {pool_id}:{day}, bucket ids are {pool_id}:{day}:{bucket_index}. Pool stats fields: day, tx_count, volume_usd, tvl_usd; pool buckets add bucket_index, sample_count, fees_usd, log_sum, log_sum2.

With a days or start_date/end_date window, the pool resource also carries window_stats (window sums: tx_count, volume_usd, tvl_usd, fees_usd) and an apr attribute computed with the same fee-rate / TVL-reliability math as /api/routes/analyze: 

# Window + APR for a pool (fee tier applied to volume, annualized over the window)
curl "http://localhost:8000/api/pool/165681/daily-stats?days=30"

curl "http://localhost:8000/api/pool/165681/daily-stats?start_date=2026-08-01&end_date=2026-08-15"

# Sparse: window aggregate + APR only
curl "http://localhost:8000/api/pool/165681/daily-stats?fields=pool[window_stats,apr]"

Auth

Most analytic endpoints require HTTP Basic auth (PORTAL_USERNAME/PORTAL_PASSWORD). Public endpoints: /api/coins/list, /api/coins/search-by-symbol, /api/coin-families, /api/coin/price-history, the pages, and static assets.
